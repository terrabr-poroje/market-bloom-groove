# گزارش بررسی فقط‌خواندنی ترابار — ۳ نوامبر ۲۰۲۶

## دامنه و محدودیت
این گزارش از بررسی فقط‌خواندنی GitHub و پروژه Supabase با شناسه `gznsxqeyhnuzglliijzz` تهیه شده است. هیچ جدول، رکورد، policy، function، secret، تنظیمات احراز هویت، DNS، Worker یا سرویس میزبانی تغییر نکرده است.

## وضعیت ساختار
- ۲۷ جدول در schema عمومی مشاهده شد.
- RLS برای هر ۲۷ جدول فعال بود.
- فهرست migrationهای ثبت‌شده تا migration مربوط به درخواست برداشت فروشنده در ۲۸ اکتبر ۲۰۲۶ مشاهده شد.
- پنج Edge Function فعال مشاهده شد: `quick-processor`، `admin-login`، `admin-manage-city-manager`، `free-sms-setup-check` و `free-sms`.

## یافته مهم: مسیر انتشار بار در quick-processor
تابع فعال `quick-processor` با `SUPABASE_SERVICE_ROLE_KEY` به دیتابیس متصل می‌شود. در شاخه `publish_load`، تابع وجود رکورد عضو را بررسی می‌کند و سپس با دسترسی service role رکورد بار را درج می‌کند. در همین مسیر، کنترل صریح `verification_status` یا تأیید نقش `supplier/bar_seller` دیده نشد.

این موضوع با قاعده محصول ترابار مبنی بر انتشار بار فقط توسط فروشنده/تأمین‌کننده تأییدشده بالقوه تعارض دارد؛ زیرا service role کنترل‌های RLS را دور می‌زند. با این حال، جست‌وجوی کد مخزن برای `quick-processor`، `Terrabar-api` و `publish_load` فراخوانی برنامه‌ای مستقیمی پیدا نکرد. این نتیجه فقط نبود ارجاع در کد مخزن را نشان می‌دهد و مصرف‌کننده خارجی یا فراخوانی مستقیم از محیط‌های دیگر را رد نمی‌کند. همچنین در لاگ‌های ۲۴ ساعت اخیر Edge Function هیچ درخواست ثبت‌شده‌ای برای `quick-processor` دیده نشد؛ این فقط عدم مشاهده در پنجره لاگ بررسی‌شده است، نه اثبات عدم استفاده.

**اقدام لازم پیش از هر اصلاح:** شناسایی مصرف‌کننده‌های واقعی تابع از طریق لاگ‌های Edge Function و بررسی تنظیمات/کلاینت‌های منتشرشده. تا آن زمان تابع نباید حذف، غیرفعال یا تغییر داده شود.

## وضعیت اتصال OTP به Free SMS
- فایل `src/routes/auth.tsx` برای ارسال کد، مستقیماً `supabase.auth.signInWithOtp({ phone })` را فراخوانی می‌کند و برای تأیید کد از `supabase.auth.verifyOtp({ phone, token, type: 'sms' })` استفاده می‌کند.
- در کد برنامه، هیچ فراخوانی‌ای به Edge Function با نام `free-sms` پیدا نشد. بنابراین تابع Free SMS فعلی به مسیر ورود/ثبت‌نام OTP وصل نیست.
- تابع `free-sms` فقط `action=test` را می‌پذیرد و گیرنده را به شماره آزمایشی ثابت محدود می‌کند؛ برای OTP عمومی طراحی نشده است.
- تابع setup-check فقط تنظیمات وجودی و WSDL را بررسی می‌کند و پیامک نمی‌فرستد.
- نتیجه: حتی اگر تست تابع آزمایشی روزی موفق شود، OTP سایت تا زمانی که ارائه‌دهنده SMS در تنظیمات Supabase Auth به‌درستی تنظیم و با کد واقعی آزمایش نشود، از این تابع استفاده نخواهد کرد.

## وضعیت پیامک Free SMS
- `free-sms` فقط `action=test` را می‌پذیرد.
- گیرنده پیامک باید دقیقاً برابر `FREESMS_TEST_RECIPIENT` باشد.
- تابع WSDL را می‌خواند و سپس درخواست آزمایشی می‌فرستد؛ موفقیت HTTP به‌تنهایی تحویل پیامک را ثابت نمی‌کند.
- `free-sms-setup-check` فقط وضعیت پیکربندی و دسترسی WSDL را می‌سنجد و پیامکی ارسال نمی‌کند.
- در لاگ‌های ۲۴ ساعت اخیر چهار درخواست به `free-sms` مشاهده شد: سه پاسخ 400 و یک پاسخ 502. اجرای 502 با خطای قبلی WSDL هم‌راستا است؛ پیامک تحویل‌شده محسوب نمی‌شود. این درخواست‌ها مربوط به endpoint آزمایشی‌اند و نشان‌دهنده فراخوانی از مسیر ورود کاربران نیستند. در نتیجه، هیچ‌یک از این دو تابع در وضعیت مشاهده‌شده، مسیر کامل OTP واقعی برای ورود کاربران نیست.

## بازبینی ویترین اختصاصی و سیاست‌های مشاهده بار
بررسی کد `src/routes/store.$memberId.tsx` و تابع زنده `get_storefront_member(uuid)` نشان داد:
- مسیر ویترین برای کاربر واردنشده ابتدا صفحه ورود نشان می‌دهد؛ داده ویترین پس از احراز هویت درخواست می‌شود.
- تابع فقط اعضایی را برمی‌گرداند که حداقل یک نقش حرفه‌ای approved از نوع supplier/bar_seller/seller دارند.
- خروجی RPC محدود به شناسه، نام، شهر، نقش و وضعیت تأیید است.
- کد مخزن و توضیح معماری در baseline تصریح می‌کند که این RPC برای نمایش هویت حداقلی عضو تأییدشده طراحی شده تا RLS جدول members بازتر نشود.
- بارها و tierهای قیمت از مسیر عادی Supabase خوانده می‌شوند و تابع SECURITY DEFINER برای دورزدن RLS بارها به کار نرفته است. سیاست زنده `loads_select_authorized` محدودیت‌های دسترسی بار را اعمال می‌کند؛ سیاست tierها نیز فقط tierهای بار قابل مشاهده را برمی‌گرداند.

**نتیجه:** هشدار قبلی درباره `get_storefront_member` به‌عنوان خطر احتمالی، با توجه به طراحی مستندشده، فعلاً یک رفتار عمدی و کنترل‌شده به نظر می‌رسد؛ اقدام اصلاحی لازم تشخیص داده نشد. این تابع تغییر نکرد.

## بازبینی جزئی هفت تابع SECURITY DEFINER
مجوز اجرا برای هر هفت تابع بررسی شد: نقش `anon` اجازه اجرا ندارد؛ نقش‌های `authenticated` و `service_role` اجازه اجرا دارند. مالک همه توابع `postgres` است.

| تابع | نتیجه بررسی بدنه |
|---|---|
| `get_storefront_member(uuid)` | فقط عضو دارای نقش supplier/bar_seller/seller با وضعیت approved را برمی‌گرداند؛ اما هر کاربر authenticated می‌تواند UUID عضو واجد شرایط را ارائه کند. خروجی شامل نام، شهر، نقش و verification_status است. باید مشخص شود این داده‌ها برای ویترین عمومیِ اعضای واردشده طراحی شده‌اند یا خیر. |
| `terrabar_admin_archive_load(uuid)` | قبل از بایگانی، مدیر کل یا مدیر شهر فعال همان شهر را کنترل می‌کند؛ رویداد audit ثبت می‌شود. |
| `terrabar_admin_archive_member(uuid)` | قبل از بایگانی عضو، مدیر کل یا مدیر شهر فعال همان شهر را کنترل می‌کند؛ رویداد audit ثبت می‌شود. |
| `terrabar_admin_restore_load(uuid)` | بازگردانی را فقط به مدیر کل محدود می‌کند؛ رویداد audit ثبت می‌شود. |
| `terrabar_admin_restore_member(uuid)` | بازگردانی را فقط به مدیر کل محدود می‌کند؛ رویداد audit ثبت می‌شود. |
| `terrabar_order_pricing_valid(...)` | فقط تطابق قیمت/مقدار سفارش با tier یا قیمت پایه بار را به‌صورت boolean بررسی می‌کند؛ عملیات نوشتن ندارد. |
| `terrabar_request_seller_payout(...)` | به ورود کاربر، اتصال member به auth.uid، مالکیت حساب بانکی، تأیید حساب و مانده قابل تسویه محدود است؛ درخواست و audit ثبت می‌کند. |

در بررسی بدنه‌ها، برای پنج تابع مدیریتی کنترل نقش/محدوده شهر، و برای تابع تسویه کنترل مالکیت و مانده مشاهده شد. یافته‌ای که نیازمند تصمیم محصولی و بررسی مصرف‌کننده است، دامنه دسترسی تابع ویترین `get_storefront_member` است؛ فعلاً هیچ ACL یا تابعی تغییر نکرده است.

## هشدارهای Supabase مشاهده‌شده
### امنیت
- ۷ جدول دارای RLS بدون policy: `admin_recovery_codes`، `outgoing_messages`، `social_connections`، `social_contacts`، `social_messages`، `social_posts` و `webhook_events`. این می‌تواند طراحی عمدی برای مسدودکردن دسترسی مستقیم باشد؛ policy اضافه نشود مگر پس از بررسی مصرف‌کننده.
- ۷ تابع SECURITY DEFINER برای نقش authenticated قابل اجرا هستند؛ از جمله توابع storefront، archive/restore، اعتبارسنجی قیمت سفارش و درخواست برداشت. هشدار Advisor به‌تنهایی اثبات آسیب‌پذیری نیست؛ بدنه، ACL و منطق احراز نقش باید جداگانه بررسی شود.
- حفاظت رمزهای افشاشده در Auth غیرفعال است.

### کارایی
- ۶ کلید خارجی بدون ایندکس پوششی.
- ۲ هشدار بهینه‌سازی ارزیابی auth در policyهای RLS.
- ۱۳ مورد multiple permissive policies.
- ۳۱ ایندکس استفاده‌نشده؛ حذف هیچ ایندکسی بر اساس این هشدار به‌تنهایی مجاز نیست.

## مستندات بیرونی سرویس‌دهنده پیامک
جست‌وجوی عمومی برای دامنه `payammatni.com` یک بسته ثالث در Packagist پیدا کرد که از SOAP و نام کاربری/رمز پنل استفاده می‌کند؛ اما همان بسته صراحتاً می‌گوید آدرس WSDL نمونه است و باید آدرس واقعی از پنل یا مستندات رسمی سرویس‌دهنده دریافت شود. بنابراین این منبع، endpoint و نام متد معتبر را اثبات نمی‌کند و نباید بر اساس آن SOAP envelope یا endpoint دیگری حدس زده شود. (منبع: https://packagist.org/packages/smpackbuilder/laravel-payammatni-sms)

فعال‌سازی SOAP در هاست نیز به‌تنهایی خطای HTTP 403 هنگام خواندن WSDL را رفع نمی‌کند؛ تا وقتی سرویس‌دهنده WSDL واقعی، متد، پارامترها و محدودیت IP را کتبی تأیید نکند، مسیر فعلی متوقف می‌ماند.

## اقدامات انجام‌نشده
1. بررسی لاگ‌های تابع `quick-processor` برای تعیین استفاده واقعی و شناسایی actionهای فراخوانی‌شده، بدون نمایش داده شخصی یا payload حساس.
2. بررسی جداگانه هفت تابع SECURITY DEFINER و مصرف‌کنندگان آنها.
3. بررسی اثر فعال‌سازی leaked-password protection بر تجربه ورود و سیاست رمز.
4. تکمیل مسیر OTP پس از دریافت مستندات قطعی Free SMS؛ endpoint یا SOAP method نباید حدس زده شود.
5. حل امن secret نامعتبر `SUPABASE_ACCESS_TOKEN` در GitHub Actions؛ token نباید در چت یا لاگ ظاهر شود.
