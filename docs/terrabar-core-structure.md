# ترابار — ساختار اصلی و نقشه تطبیق

**وضعیت:** سند کاری برای تطبیق؛ هنوز به معنی تأیید اجرای مهاجرت یا تغییر دیتابیس زنده نیست.  
**مخزن:** `terrabr-poroje/market-bloom-groove`  
**Supabase مرجع:** `gznsxqeyhnuzglliijzz`  
**قاعده:** دیتابیس جدید نسازید، جدول/داده را حذف نکنید و SQL را مستقیم روی Production اجرا نکنید. تغییرات باید در migration بازبینی‌شده و با آزمون نقش‌ها ارائه شوند.

## 1. مرجع‌های محصول

- اسناد تأییدشده «سند اصلی» و «سند اصلی تکمیلی» ترابار و پیش‌نمایش‌های تأییدشده مرجع نیازمندی‌ها هستند.
- رابط کاربری فارسی و راست‌چین با هویت سبز/سفید.
- مسیرهای اصلی: `/auth` (ورود/ثبت‌نام)، `/announce` (اعلام بار)، `/requests` (جست‌وجو و درخواست بار).
- «طراحی با ChatGPT، اجرا با امیر»: هیچ انتشار یا تغییر مخرب در دیتابیس زنده بدون تأیید روشن انجام نشود.

## 2. نقش‌ها و قواعد دسترسی موردنیاز

| نقش | قاعده موردنیاز |
|---|---|
| تأمین‌کننده | درخواست عضویت حرفه‌ای؛ اعلام بار فقط پس از تأیید |
| بارفروش / حجره‌دار | درخواست عضویت حرفه‌ای؛ اعلام بار فقط پس از تأیید |
| خریدار عادی | مشاهده بارهای مجاز در شهر خودش؛ ثبت درخواست خرید |
| خریدار ویژه | شهر خودش و شهرهای همسایه فعال، طبق جدول شهرهای همسایه |
| خریدار حرفه‌ای (Pro) | بدون فیلتر شهر، مطابق دسترسی تأییدشده |
| مدیر شهر | فقط شهرها و سفارش‌های محدوده واگذارشده؛ هماهنگی سفارش‌های محدوده خودش |
| مدیر کل | مدیریت سراسری، شهرها، تخصیص مدیران و مجوزها |

- یک حساب می‌تواند در آینده چند نقش تأییدشده داشته باشد.
- انتخاب نقش هنگام ثبت‌نام به‌تنهایی مجوز حرفه‌ای ایجاد نمی‌کند؛ تأیید باید سمت سرور/دیتابیس اعمال شود.
- اطلاعات تماس و نشانی خریدار و فروشنده نباید مستقیم در اختیار طرف مقابل قرار گیرد؛ هماهنگی از مسیر مدیران شهری است.
- تحویل حضوری فقط پس از پرداخت آنلاین؛ تأیید تحویل با OTP یا QR. پرداخت هنگام تحویل حضوری مجاز نیست.
- نشانی خریدار فقط برای تحویل درب محل لازم است؛ برای دریافت حضوری نشانی ثبت نشود.

## 3. ساختار مفهومی داده

1. **هویت و عضویت:** Supabase Auth، پروفایل/عضو، درخواست عضویت، نقش‌های متعدد و وضعیت تأیید.
2. **جغرافیا و مدیریت:** شهرها، شهرهای همسایه، مدیران، تخصیص مدیر به شهر و ثبت رویدادهای مدیریتی.
3. **کالا و بار:** محصول و رقم به‌صورت جدا؛ کیفیت ویژه/استاندارد/اقتصادی/توافقی؛ وزن بسته، تعداد بسته، حداقل سفارش، قیمت و بازه‌های قیمت، موجودی، وضعیت و تصاویر.
4. **درخواست خرید و سفارش:** درخواست‌های چندقلمی در صورت نیاز، تاریخ/کیفیت/مقدار، سفارش، وضعیت پرداخت، روش تحویل و تأیید تحویل.
5. **حریم خصوصی و پیگیری:** اطلاعات تماس محدودشده، پیام‌های سیستمی، تاریخچه تغییرات و گزارش ممیزی.

این بخش مدل مفهومی است، نه دستور ساخت فوری جدول‌های تکراری. ابتدا باید مدل با جداول زنده تطبیق داده شود.

## 4. یافته‌های تطبیق اولیه (نیازمند بررسی)

- Snapshot موجود در شاخه `automation/supabase-schema-snapshot` شامل ۱۹ جدول عمومی است و RLS روی هر ۱۹ جدول فعال گزارش شده.
- در Snapshot، برای ۸ جدول `orders`, `outgoing_messages`, `purchase_requests`, `social_connections`, `social_contacts`, `social_messages`, `social_posts`, `webhook_events` هیچ policy تعریف‌شده‌ای دیده نشده است. این موضوع باید با نیازهای دسترسی و روش استفاده از service role بررسی شود.
- Snapshot برای بعضی جدول‌ها مجوزهای گسترده‌ای به `anon` و `authenticated` نشان می‌دهد. فعال‌بودن RLS به‌تنهایی جایگزین بازبینی grants و policyها نیست.
- ناسازگاری مهمی بین کد فعلی و Snapshot وجود دارد: کد فعلی از `user_roles` می‌خواند و فیلدهای `loads` مانند `product_name`, `seller_id`, `package_weight_kg` را استفاده می‌کند؛ اما Snapshot زنده‌نما جدول `member_roles` را نشان می‌دهد و ساختار `loads` آن شامل فیلدهایی مانند `name`, `quantity`, `member_id`, `price` است. پیش از تغییر، باید تأیید شود که برنامه به همین پروژه و schema متصل است و Snapshot واقعاً از همان دیتابیس فعلی گرفته شده است.
- در فایل کد فعلی، صفحه درخواست بار از داده‌های نمونه محلی استفاده می‌کند؛ بنابراین نمایش فعلی به‌تنهایی اتصال واقعی و فیلترهای امنیتی را ثابت نمی‌کند.

## 5. ترتیب اجرای امن

1. تثبیت snapshot از همان پروژه Supabase و بررسی URL/Project Ref بدون نمایش کلیدهای محرمانه.
2. مقایسه دقیق جداول و ستون‌های زنده با `src/integrations/supabase/types.ts` و استفاده‌های `supabase.from(...)` در کد.
3. تهیه ماتریس CRUD و RLS برای هر نقش؛ آزمون جداگانه با کاربر عادی، ویژه، حرفه‌ای، فروشنده تأییدنشده، فروشنده تأییدشده، مدیر شهر و مدیر کل.
4. نوشتن migrationهای کوچک و قابل بازگشت در شاخه جدا؛ هیچ تغییر مستقیم در Production در مرحله طراحی.
5. اجرای آزمون build و آزمون policyها؛ بررسی diff؛ سپس ارائه Pull Request برای بازبینی.
6. فقط پس از تأیید روشن، اعمال migration در Supabase و سپس انتشار کد هماهنگ.

## 6. معیار پایان تطبیق

- کد، TypeScript Database Types و schema واقعی از نظر نام جدول/ستون هماهنگ باشند.
- نقش و شهر فقط با policy سمت سرور/دیتابیس کنترل شوند؛ فیلتر رابط کاربری به‌تنهایی کافی نیست.
- سفارش‌ها و درخواست‌ها فقط برای مالک و مدیر مجاز قابل مشاهده باشند.
- اطلاعات تماس/نشانی طرفین برای طرف مقابل افشا نشود.
- تغییرات روی شاخه و PR بررسی شوند؛ snapshot خام هرگز مستقیماً به‌عنوان migration اجرا نشود.
